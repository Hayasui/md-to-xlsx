# 升级路线图与需求提报指南

本文件记录技能的**能力边界**、**改进候选**和**提需求的方式**。
目的是让未来的升级有据可依，而不是每次从零讨论。

---

## 一、当前能力边界（诚实清单）

### 已经做得很好的

| 能力 | 说明 |
|------|------|
| 样式固化 | 字体、配色、行高、边框、打印设置全部写死在代码里，不需要每次重调 |
| 结构固化 | 三类表的列定义、合并逻辑、区块分隔已定型；每类实例数可变 |
| 自动校验 | 保存后自动检查行高裁切、合并重叠、Markdown 残留、字体、打印设置 |
| 自动备份 | 目标文件存在时先存 `_backup/`，避免覆盖用户手动修改 |
| 中英分列字体 | 中文列微软雅黑、英文列 Aptos，跨列合并自动用中文字体 |

### 仍需人工的（这是痛点所在）

| 环节 | 现状 | 工作量 |
|------|------|--------|
| **内容转写** | 把 md 内容改写成 Python 字面量填进 `NEEDS/SURVEY/OUTLINE_*` | 最大，约 100–150 行手写 |
| **从过程稿提取问卷** | 输入可能是设计稿，要从方案对比与论证里把定了的那版问卷摘出来 | 中高 |
| **面向需求方删减** | 靠 AI 逐条判断哪些是"非必要文字" | 中等 |
| **中英比对** | 由 AI 逐条读 `_EN` 版核对，脚本不参与 | 中等 |
| **一致性检查** | 同质信息写法是否统一，靠人工过 | 小 |
| **题号完整性** | 靠人工确认问卷 Q1-Qn、每份大纲 Q1-Qn 是否齐全 | 小 |
| **md 改动后同步** | 重新生成会丢工具重算的行高，只能手工比对 | 中等 |
| **用户 xlsx 改动的回写** | 逐格 diff 能找全，但比对与同步仍要手工 | 小 |

**关键结论**：样式和结构已经不需要再讨论了。
真正的摩擦集中在「**md → Python 字面量**」这一道人工转写上。
未来的升级价值，主要就在这里。

### 已知未解决（记录在案）

| 问题 | 现状 | 备注 |
|------|------|------|
| **八列版横宽** | 总列宽约 220，A4 横向可用约 149，打印/导 PDF 会缩到约 68%（10pt 字实际约 6.8pt） | 屏幕阅读不受影响。可选方案：接受跨页、压列宽，或给需求方单独出一版去掉「观察记录点」列。尚未与用户定案 |
| **内容转写仍是手写** | 每项目约 100-150 行 Python 字面量 | 最值得投的升级点，但改动面大 |
| **过程稿提取靠人读** | 输入是设计稿时，要人工判断哪些章节进表 | 判断本身难自动化，但"不进表清单"可以持续补充 |
| **中英同格的边界** | 目前只有色名这类单字类别走了中英同格（`红（Red）`） | 什么情况该同格、什么情况该分列，还没有稳定的判据 |

## 一·五、已经吸收进规范的教训（按时间倒序）

### 2026-09-10 · K3P 泛娱乐审美研究

输入是一份设计过程稿（v0.1 → v0.7 七轮迭代），输出是两张表：需求梳理与纯中文的
题材偏好问卷。这次带出来的规范更新最多，因为它是本技能第一次处理**非甄别类问卷**。

| 发现 | 落到哪里 |
|---|---|
| 技能定位从"测试材料整理"扩为"用研交付物整理"，满意度 / 偏好类问卷纳入 | SKILL.md 标题与「表的组成」 |
| 问卷末列统一叫「问卷逻辑」，不再叫「判定」；列名统一，语义由内容决定 | SKILL.md「问卷逻辑」一节；format-spec.md 表格 2 |
| 逻辑记在**触发它的选项行**上，不写在被依赖的题目上 | SKILL.md / format-spec.md 同上 |
| 问卷增加纯中文规格 `survey_cn`（中文定稿在先、英文未做是常态，不是例外） | scripts 新增 `build_survey_cn`；SKILL.md 第 3 步；format-spec.md 表格 2 |
| 输入常是**设计过程稿**，需要一套提取原则与"不进表"清单 | SKILL.md 第 1 步；format-spec.md 第〇节 |
| **需求梳理表的删减尺度松一档**，分析口径留不留看读者是谁 | SKILL.md「核心目的」；format-spec.md 第〇节 |
| 「不需要改代码」只对实例数成立；新增表类型要改四处 | SKILL.md 第 3 步末 |
| 校验脚本改为两级查找（同目录 → 技能目录），找不到时明确提示后果 | scripts `load_validator()`；SKILL.md / README「使用前提」 |
| 表名跟随用途：问卷按用途命名，大纲按形式命名 | SKILL.md「表名跟随问卷用途与访谈形式」 || 题号用连续数字，不用 `Q4a` / `Q4b` 分支写法 | SKILL.md「术语中文化」；format-spec.md 一·五节 |
| 非必答写在题型列（`简答（非必答）`），不缀「（选填）」也不单开一列 | 同上 |
| 「选择题 + 附加文本输入」是平台前提，不成立时题号整体重排 | SKILL.md「问卷逻辑」一节末；format-spec.md 表格 2 |
| 玩家可见的引导语若 md 里没有，**索取原文，不要代拟** | SKILL.md 第 2 步 |
| 中文单字类别名容易混淆时，中英并列写在同一格（`红（Red）`） | format-spec.md 表格 2、四·5 |
| 用户 xlsx 改动的回写流程（逐格 diff + 读 app.xml 判断工具） | SKILL.md「用户手动改过 xlsx 之后怎么回写」；format-spec.md 五·五节 |
| 一致性检查新增两条：同一层级的称呼是否只有一种说法；中文单字类别名是否易混淆 | SKILL.md「一致性检查」 |
| 命令行开关写在前会被当成文件名，静默生成一个叫 `--no-backup` 的文件 | `main()` 先过滤 `--` 开头的参数再取文件名 |

**不吸收进规范的**：K3P 的颜色选项表（色相家族的具体取舍）、题材选项表的热度研究结论
——那些是项目内容，不是转换规范。

### 2026-09-09 · 2609 V2 与组长对齐后

组内把生成的 xlsx 拿去腾讯文档重做了一版（V2），带来四条规范层面的更新：

| 发现 | 落到哪里 |
|---|---|
| 文档核心目的是给需求方看，非必要文字全删 | SKILL.md「核心目的」+「删减清单」；format-spec.md 第〇节 |
| 题型列改用中文简述，NPS 不翻译，不标区间 | SKILL.md「术语中文化」；format-spec.md 一·五节 |
| 表 3 名字跟随访谈形式 | SKILL.md「表名跟随问卷用途与访谈形式」；format-spec.md 表格 3 |
| 腾讯文档另存会丢样式（字体 / 冻结 / 打印） | SKILL.md / format-spec.md「覆盖策略」 |

同时纠正一处 md 自身的历史错误：题 7 / 题 8 的题型标 `Rating scale · 0-10`，
题干却写「1 分最低，10 分最高」——实际是 1-10。**区间只在一处写**就不会打架。

**不吸收进规范的**（避免把一次性数据当规范）：

- 项目的样本条件（年龄、性别、游戏筛选标准）——每次都不一样
- 组长在稿子上划的黄色高亮——个人审阅标记
- 「游戏内容记录」表——测试过程中的观察记录，不属于 md → xlsx 的转换范围

## 二、改进候选（按优先级）

### P0 · 值得优先做

#### 1. md 解析器 —— 直接把 md 转成内容区

**问题**：每次要手工把 md 的题干、选项、量表抄成 Python 字面量，容易抄错、耗时。

**方案**：写一个 `parse_md.py`，识别 md 里的固定结构（`#### Q1.` 题干、编号选项、
`> 判定`、`**题干**`、`**量表标签**`、`#### 题 N　[题型]`），自动生成内容区代码。

**注意**：md 的实际格式并不统一（2609 的两份 md 格式就有差异），
所以解析器需要**容错 + 人工兜底**：解析不出的部分输出 TODO 标记，而不是静默丢弃。

**价值**：高。**成本**：中高。**风险**：md 格式变动会导致解析失败，需要保留手工兜底路径。

#### 2. 中英自动比对 ✅ 已落地（移交 sc-to-en）

**问题**：现在靠 AI 逐条读，容易漏（2609 就漏了「1-2 个词」vs「2-3 words」）。

**落地方式**：由 **`sc-to-en` 的 `lint_usertesting.py --sc`** 统一负责中英结构比对
（题号配对、选项数、量表端点），本 skill 不再自带 `compare_bilingual.py`，
避免两套逻辑漂移。生成 xlsx 前先跑：

```bash
python ../sc-to-en/scripts/lint_usertesting.py <英文版.md> --sc <中文版.md>
```

#### 3. 题号完整性检查

**问题**：`format-spec.md` 要求人工确认 Q1-Q9 / Q1-Q28，但脚本没做。

**方案**：在 `validate_xlsx.py` 里加检查——扫出所有题号，
报告缺失或重复。

**价值**：中。**成本**：低。**风险**：低。

#### 4. 删减清单的自动检查

**问题**：面向需求方的删减目前靠 AI 逐条判断，容易漏——
2609 V2 就出现过「性别」去了「（由平台定向筛选）」而「年龄」还留着这类不统一。

**方案**：在 `validate_xlsx.py` 里加一组扫描：命中平台名 / 测试形式 /
「研究落点」「内部备注」「本研究的核心品类」等关键词就报警，
提示"这可能是该删掉的内部内容"。

**注意**：只能提示，不能自动删——「问卷逻辑」列这类看似内部的词其实要保留，
最终仍由 AI 判断。

**价值**：中高。**成本**：低。**风险**：低（误报可由 AI 过滤）。

#### 5. 问卷逻辑的自洽检查

**问题**：跳转逻辑现在靠人写，写了「跳转到 Q6」而 Q6 不存在、或者两个选项的
跳转互相矛盾，脚本都不会报。K3P 那份有九条逻辑，全靠肉眼核对。

**方案**：在 `validate_xlsx.py` 里解析「问卷逻辑」列，做三项检查——
跳转目标题号是否存在；同一题的多个跳转是否造成不可达的题；最后一个板块的
跳过项是否写成了「本模块结束」而非指向不存在的题号。

**价值**：中。**成本**：低。**风险**：低（正则解析，措辞变化时可能漏报）。

#### 6. 同一层级称呼的一致性提醒

**问题**：K3P 稿子里「模块」「板块」「品类节」「第 X 部分」混用，
读者要自己判断是不是同一层。这类问题脚本查不出，靠人通读。

**方案**：在 `validate_xlsx.py` 里统计高频名词，把近义词（模块 / 板块 / 部分 /
章节）并列出现的情况报出来，由 AI 判断。

**价值**：中。**成本**：低。**风险**：中——近义词表要维护，误报可能较多。

### P1 · 有用但非必要

#### 7. 增量更新（保留用户手动排版）

**问题**：md 改动后重新生成，会覆盖 WPS 重算过的行高。

**方案**：读入已有 xlsx，只更新文本内容，保留原有的行高与格式。

**价值**：中高（针对你的实际工作流）。**成本**：高（合并逻辑复杂）。
**风险**：中——可能引入难以排查的格式错乱。

#### 8. 逐格 diff 的小工具

**问题**：用户改过 xlsx 之后回写，要现写一段 diff 代码（K3P 与 2609 都写过一遍）。

**方案**：把那段逐格比对做成 `scripts/diff_xlsx.py <用户版> <脚本版>`，
输出差异格清单，顺带报出文件是哪个工具保存的。

**价值**：中高（回写是高频动作）。**成本**：低。**风险**：低。

#### 9. HTML 预览

**问题**：本环境 COM 被拦，无法渲染 xlsx 看效果，只能靠校验器数值推断。

**方案**：额外输出一份 HTML，用表格复刻排版，方便快速肉眼确认。

**价值**：中。**成本**：中。**风险**：低。

#### 10. 回归测试基线

**问题**：改脚本后不知道有没有弄坏已有功能。

**方案**：把 2609 的内容存成 `tests/fixture_2609.py`，
每次改动后跑一次，与基线逐格比对。

**价值**：中高（长期维护必需）。**成本**：低。**风险**：低。

### P2 · 不建议做

- **完全数据驱动的 JSON/YAML 内容格式** —— 写长题干会很难受，不如 Python 字面量直观
- **图形化配置界面** —— 投入产出比低
- **支持更多文档类型（PPT、Word 输出）** —— 超出本技能职责，应该另建技能

## 三、怎么提出升级需求

### 原则：描述摩擦，不要指定实现

升级需求最有价值的部分是**你实际遇到的卡点**，而不是你设想的解决方案。
因为 AI 能看到代码，但看不到你操作时的体感。

**好的提法**：

> 这次改完 md 重新生成，WPS 里调的行高又没了，每次都要手动再调一遍。

—— 描述的是现象和痛感，方案空间留给我。

**差的提法**：

> 给我加个增量更新功能，用 openpyxl 读原文件然后只改 value。

—— 指定了实现，反而限制了解法（也许更简单的方案是「生成时从 v1 文件继承行高」）。

### 提需求时带上三样东西

1. **触发场景**：你在做什么任务时卡住的（哪个项目、哪一步）
2. **期望结果**：你希望看到什么变化
3. **实际结果**：现在发生了什么（最好带截图或具体文件）

### 一个有效的句式

> 我在【做 XX】的时候，希望【YY】，但现在【ZZ】。

例：
> 我在把 2609 的 md 转成 Excel 的时候，希望不用手抄题干，
> 但现在要把几十道题逐条改写成 Python 字面量，很容易抄漏。

### 提完需求后必做的一件事

**跑回归测试**。任何改动都可能弄坏已有功能（比如字体分列、合并逻辑）。
建议每次升级后，用同一份 md 重新生成一次，与上一版逐格比对。

## 四、维护提醒

- **Aptos 字体**：本机未安装。如果发给用旧版 Office 或 WPS 的同事，
  可能回退成默认字体。需要兼容时改 `FONT_EN = "Calibri"`。
  注意：文件被腾讯文档打开另存后，字体一律会变成等线——这是工具副作用，
  重新生成时脚本会自动改回 Aptos，不用手动处理。
- **md 格式漂移**：如果未来 md 的标题层级、编号方式变了，
  解析器和提取规则都要跟着改。提需求时说明 md 哪里变了。
- **文档与实现的落差**：`SKILL.md` 里的「列出中英不一致之处」目前是
  **AI 人工完成**，不是脚本能力。若希望自动化，就是上面 P0-2。
