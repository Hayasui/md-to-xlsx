# md-to-xlsx

本仓库把用研的中文 Markdown 文档转成可直接交付需求方的 Excel。输入是定稿的 Markdown，输出是按用途分表的表格文件，用于上传在线文档留档，或作为评审时的沟通底稿。

一份用研材料有三种读者：玩家读题干与选项，研究团队读研究落点与内部备注，需求方（运营与产品）只看三件事，要测什么、怎么筛人、问什么问题。本仓库服务的是最后一种读者，做法是剥掉 Markdown 里那层内部工作痕迹，只留需求方看得懂的内容，排成表格。

## 三类表，份数由项目决定

交付物由三类表组成：需求梳理、问卷、访谈大纲。

每类的份数不固定。最常见的是三张：需求梳理、玩家筛选问卷，加一份访谈大纲。项目如果同时做了无主持人和有主持人两个版本，大纲就是两份，一共四张。也遇到过只有问卷、没有大纲的项目，以及一个项目出两份不同用途问卷的情况。

所以表按类别组织，不是按"第几张"写死的。配置就是一张表清单，列表顺序即工作表顺序，加减条目不涉及改代码：

```python
"sheets": [
    {"type": "needs",     "name": "需求梳理",     "content": NEEDS},
    {"type": "survey",    "name": "玩家筛选问卷", "content": SURVEY},
    {"type": "outline",   "name": "无主持人访谈大纲", "content": OUTLINE_UNMODERATED},
    {"type": "outline",   "name": "有主持人访谈大纲", "content": OUTLINE_MODERATED,
     "columns": COLUMNS_8},
    # {"type": "survey_cn", "name": "题材偏好问卷", "content": SURVEY_CN},
]
```

问卷有两种列规格。中英并列的 `survey` 五列，纯中文的 `survey_cn` 四列，两者共用同一个构建函数，行格式只差英文那一格。中文定稿在先、英文版还没做的时候，先用 `survey_cn` 出一版，等英文做完再换回来，这是流程的常态，不是例外。表名也跟着用途走：甄别问卷叫「玩家筛选问卷」，满意度或偏好类问卷叫「题材偏好问卷」或「满意度问卷」。

访谈大纲同样有两种列规格。无主持人版六列；有主持人版通常八列，多出「追问方向」和「观察记录点」。主持人版 Markdown 里是提问话术、追问方向、观察记录点三栏，落到表里就是这三处：话术进题干位，追问与记录各占一列。

列规格在配置里显式写出，脚本不做推断。推断会犯错得不声不响：某一版恰好没写追问行，两列就静默消失，表头和列宽跟着变，还不报错。显式声明则相反，用了追问行却没声明对应列，脚本当场抛错。

## 末尾那一列写什么

问卷的末列统一叫「问卷逻辑」，记录题目之间的跳转与因果关系。它和流程图上的箭头是同一件事，落到表里就是"选了这一项之后会发生什么"：跳过整个板块就写「跳转到 Q6」，最后一个板块跳过就写「本模块结束」，互斥选项写「与其余色调选项互斥」，选项触出文本框写「需填写文本」。

甄别问卷里这一列写的是终止与通过。列名统一，语义由内容决定，不必为两种问卷维护两套列名。

有一条写法上的规矩：**逻辑记在触发它的那一行，不要写在被依赖的题目上**。早先的做法是在下属题目旁注「上一题未勾选跳过项」，读的人得反过来推导是哪条路径导致的隐藏，配置问卷时也容易漏。改成在跳过选项旁直接写「跳转到 Q6」，一处就交代清楚了。

这一列填写问卷的人看不到，它是给配置问卷的人看的，不必为了玩家可读而改写措辞。

## 目录

```
SKILL.md                        主流程（读源文件 → 确认信息 → 填内容区 → 生成校验 → 汇报）
references/
  format-spec.md                格式规范（三类表的列定义、样式、删减清单、题型映射）
  roadmap.md                    升级路线图与已知未解决项
  example-4sheets.py            实战样例：四张表的完整脚本（3D 二合首测项目）
scripts/
  build_research_xlsx.py        构建脚本模板（含样式区，填内容区即可用）
  validate_xlsx.py              生成后的自动校验，分两级：错误（行高裁切、合并重叠、Markdown 残留、字体、打印设置、题号缺失/重复、跳转目标不存在）必须修复；提醒（删减关键词命中、层级称呼混用、末板块写法）由人裁决
  check_drift.py                判断交付表生成之后有没有被人手动改过：按项目脚本重建一份到临时路径，与磁盘上的正式件逐格比对
  run_project_script.py         Windows 上跑项目脚本的壳子，绕开中文路径当命令行参数时的编码错乱
```

## 用法

复制构建脚本与校验脚本到工作目录，改「内容区」，然后生成：

```bash
python build_research_xlsx.py "【YYMM】项目简称.xlsx"
```

脚本会先备份同名旧文件到 `_backup/`（用 `--no-backup` 跳过），再生成，最后自动校验并打印问题清单。单独校验已有文件：

```bash
python validate_xlsx.py <文件.xlsx>
```

需要知道每种表怎么填时，看 `scripts/build_research_xlsx.py` 的注释与 `references/format-spec.md`；`references/example-4sheets.py` 是一份真实项目的完整脚本，长文本怎么换行、追问与观察记录行怎么用，都能从那里看。那份样例保留的是当时交付的原样，命名上早于后来的调整，写新脚本以模板为准。

## 定下来的几条原则

这是转换工具，不是编辑工具。Markdown 是源头，Excel 是渲染产物。源头写「人工复核」，表里就写「人工复核」，不改写成「机筛」或别的措辞；判断哪条筛选规则更合理，不在转换的职责里。真觉得源头的写法不妥，那就改 Markdown，让源头与产物一致。

给需求方看，意味着要主动剥掉一层：平台名称、测试形式、录屏录音方式、内部备注、研究落点，都不进表。删减本身就是格式规范的一部分，这层取舍是项目早期定下的，等同于固定的排版规则，与上一条并不冲突：剥掉哪些内容有清单可循，而内容本身的语义一个字不动。尺度还分两档，问卷表与大纲表从严，每一行都必须是玩家在平台上真正看到的东西；需求梳理表松一档，它通篇都在讲研究设计，其中的分析口径（样本量阈值、编码一致性要求）算不算"非必要文字"，取决于这份表给谁看，给组内同事的可以留，给需求方的可以省。

输入也不一定是成品稿。真实项目里更常见的是一份还在迭代的设计文档，里面有结构总览、方案对比、设计理由、编码方案、桌面研究附录，真正的问卷只占其中一节。这时先做一次提取，只把定了的那版问卷取出来，其余留在 Markdown。判断标准是：这句话是玩家会看到的、需求方要判断的，还是设计者自己要想清楚的。

还有一件事得提前认下：表格可能在 WPS 或腾讯文档里被打开、另存，字体、冻结窗格、打印设置会被改掉甚至丢失。所以样式基线不跟工具走，重新生成时一律回到脚本里的固化规范，不迁就某个工具算出的结果。要调列宽，依据是人读起来觉不觉得挤，而不是工具给出的数字。

中英两侧对不上时，脚本只指出位置，不裁决。中文稿是源头，英文稿是本地化产物，由人判断是英文漏了，还是中文后来改了而英文没跟。

## 使用前提

Python 3.8 以上，需要 openpyxl。面向游戏用研场景，材料基于 UserTesting 平台的问卷与访谈大纲。

校验依赖 `validate_xlsx.py`。脚本先在同目录找，找不到会到技能安装目录去找；两处都没有才跳过，并明确说明后果。**「已生成」三个字不代表任何校验结论**，看到"跳过自动校验"的提示，就把文件复制过去重跑。

## 许可

内部研究工具，按需自取。
